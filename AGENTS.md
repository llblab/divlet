# divlet project context

divlet is a local browser layout board for Pi agents. It edits validated static web layouts (Divlet projects: HTML elements with Tailwind classes), not arbitrary applications. Start with [README.md](README.md) for usage and [docs/README.md](docs/README.md) for technical documentation.

## Meta-Protocol Principles

- **Constraint-driven structure:** Add context or abstraction only when it preserves a real constraint or makes an existing responsibility easier to find. Consolidate stale context rather than accumulating parallel instructions.
- **Durable rules:** This file owns contributor constraints and recurring engineering guidance, not task status or delivery history.
- **Open work:** [BACKLOG.md](BACKLOG.md) is the only task backlog. Keep only remaining, blocked or gated work there.
- **Completed changes:** [CHANGELOG.md](CHANGELOG.md) records implemented outcomes. Unreleased work must not be presented as a published release.
- **Human documentation:** README files are entrypoints; `docs/` owns architecture, operational guidance and the format reference ([docs/format.md](docs/format.md)).
- **Reconciliation:** When behavior or ownership changes, update its authoritative document, reconcile affected backlog items and record meaningful delivery. Do not duplicate the same status across files.
- **Git:** The repository is local. Commit after each coherent step.

## Topology

- **`core/` and `web/` are peers** (plugins can act on either). `core/` holds the server-side core (`core/index.js` entry, `core/lib/`, `core/tests/`); `web/` is the web client (`board.js` entry, `index.html`, `board.css`; its modules, one per domain, in `web/lib/`); `plugins/` and `adapters/` sit beside them.
- **Core:** three connected parts: the Divlet format (a flexible, web-oriented JSON project description: `core/lib/model.ts`, `core/lib/project.js`), the codec between it and HTML (`core/lib/codec.js`, `core/lib/render.js`), and the web editor with its own server (`core/lib/runtime.js`, `core/lib/server.js`, `web/`). The core knows exactly one project format. See [architecture](docs/architecture.md).
- **Plugins:** everything that attaches to the core. Importer/exporter plugins (`plugins/<id>/`, today `plugins/pen/` and `plugins/html/`) are codecs between a foreign format and Divlet; the contract and registry are `core/lib/plugins.js`, `core/lib/import.js` is the generic driver. Tailwind (the style codec `core/lib/styles.js`, compilation `core/lib/styling.js`, the inspector's class/layout/spacing panels in `plugins/tailwind/web/`) is a plugin: the core reaches it only through `core/lib/engine.js` and the client panel registry `web/lib/panels.js`. A plugin's client modules are served at `plugins/<id>/<file>` and import core client modules as `../../lib/<file>`. Each plugin is a package of its own (`plugins/<id>/package.json` with its own dependencies; the repository is an npm workspace): `index.js` is only the entry point, its code lives in `plugins/<id>/lib/`, its tests in `plugins/<id>/tests/`. Plugins import from the core, never the reverse. The same shape applies at every level: a domain folder exposes an entry point and keeps its internals in `core/lib/`.
- **Adapters:** `adapters/<id>/` connect the core to a host. `adapters/pi/` is the Pi extension (`/divlet` command, the agent bridge); the skill it ships is the product's own, in `skills/divlet/` at the root, so other hosts can load or install the same file. The root package is **harness-agnostic**: its entry (`exports['.']`) is the library (`core/index.js`), the bins are the CLI and the MCP server, and a host's packaging lives in its own place — Pi's is `packages/divlet-pi` (a manifest plus `export { default } from 'divlet/pi'`, no code), so what Pi runs is always the adapter that ships in the product. `adapters/mcp/` is the MCP stdio server (`divlet-mcp`), `adapters/cli/` the standalone CLI (`divlet`). Adapters import from the core and never the reverse; like plugins they are packages (`package.json`, `index.js` entry, `lib/`, `tests/`). `core/lib/contract.js` owns the tool list, parameters, semantics and result shaping — adapters translate the representation (TypeBox, JSON Schema, text envelopes) and must not re-implement an operation. No adapter starts a service at import time.
- **Agent workflow:** `skills/divlet/` belongs to the product, not to an adapter: it is the portable workflow an agent loads (Pi finds it through the extension; other hosts install it globally). It is the product's **entry point**, written for an agent that has nothing else: install the tools (an MCP host registers `npx -y --package=divlet divlet-mcp`), open a project, then follow the loop. Keep it a walkthrough, not a reference dump — every claim it makes must be true of the code, and `core/tests/skill.test.js` enforces exactly that (tool names, CLI flags, error codes, documents, front-matter limits). It is distinct from this contributor guide.
- **Tests:** `core/tests/` (unit) and `core/tests/browser/` (browser suites); the Pi RPC scenario and its mock provider live with their adapter in `adapters/pi/tests/e2e/pi.mjs`, plugin tests in `plugins/<id>/tests/`. See [testing](docs/testing.md). Generated screenshots belong in the ignored `artifacts/` directory.

## Operating Principles

- **Language and identity:** Write project documentation and code comments in English. Keep the public identity `divlet`, the `/divlet` command and `*_divlet` tools. Tool contracts use `frames` and `frameId`; internal code may use `document` and `documentId`.
- **Format direction:** Divlet's own format is web-first and Tailwind-first: elements with Tailwind classes, shared tokens and project CSS, kept in two-way sync with the generated HTML. Styles are set declaratively and become Tailwind utilities (an arbitrary-property class when no utility exists); raw CSS stays available.
- **Plugins, not special cases:** A foreign format is an importer plugin. Never name a foreign format in the core, and never edit a foreign source in place: it is converted once into a sibling `.divlet` (an existing `.divlet` is never overwritten, an unconvertible source opens as itself with diagnostics). Imported bytes are never rewritten; the one exception is a legacy `.divlet` that still holds a foreign source — its bytes are moved to a free `<name>.pen` and the `.divlet` path becomes the converted project.
- **Source ownership:** Each `<name>.divlet` file is canonical and independently identified by its full path. Default creation is `project.divlet` in the chosen directory, without a wrapper folder. Preserve hand edits rather than silently overwriting them.
- **Output ownership:** `core/lib/output.js` owns generated-file provenance, collision checks and symbolic-link refusal. Never overwrite unowned output paths or share one output directory between projects. Generated files belong in `.divlet/<name>/` (or the project's relative `outputDir`).
- **Local filesystem model:** Projects may live and be edited anywhere permitted by the OS; referenced local resources resolve automatically, including absolute paths. Keep bounded regular-file reads, no-link checks and non-overwriting publication. This is trusted local-project access, not an arbitrary HTTP filesystem route.
- **Validated commits:** Check the expected version, prepare and validate the candidate before changing accepted state, and retain the last working state on invalid external edits. Do not bypass these rules in HTTP handlers or Pi tools.
- **History safety:** Undo/redo must validate a whole group before committing it and refuse overlapping later edits without changing state.
- **Preview trust:** A matching iframe `WindowProxy` is not authentication after navigation. Keep model, selection and editing traffic on the authenticated document-bound MessagePort; keep referrer protection and capability rotation on preview reset.
- **Serialized bridge code:** `previewBridge` and the site live script are injected through `Function#toString`; keep them free of imports and outer-scope dependencies.
- **Local HTTP boundary:** Preserve loopback binding, token-scoped routes, Host/Origin checks, CSP, request-size bounds and filesystem confinement.
- **One writer per project:** A board owns its project file and is the only writer. Clients (browser, Pi, MCP, CLI) attach to the board found in `core/lib/boards.js`; do not open a second runtime for a project another live board owns. Attached traffic uses the board's token-scoped `api/tool` route, which runs the same contract.
- **Long-lived frames:** Each artboard keeps one iframe for the project's lifetime, loaded lazily by the browser (`loading="lazy"`, eager only for selected/expanded frames). Do not reintroduce scroll/zoom-driven unmounting; swap a frame only behind a ghost of its previous page. At far zoom a cached PNG may stand in for the live page.
- **TypeScript:** The product is TypeScript. Sources are `.ts` (the browser client joins in the migration; until then its JavaScript is type-checked from the same types). Node runs the sources directly by stripping types — there is no build in the development loop — so a file's own imports name the real file (`./model.ts`), the compiler is configured `strict` with `erasableSyntaxOnly` (no enums, namespaces, parameter properties, decorators), and `npm test` starts with `tsc --noEmit`. `dist/` is generated by `npm run build` for publishing only: never edit it, never commit it. Vocabulary belongs in `core/lib/model.ts`; a module types its own boundary and treats foreign input as `unknown` until the validator accepts it.
- **Landing is published, not built:** `landing/` is plain static files for GitHub Pages — no build step, no external fonts, images, stylesheets or scripts, because only that folder ships. CI (`.github/workflows/landing.yml`) publishes it to the root of the `gh-pages` branch and only when the folder's fingerprint changed; `scripts/landing-hash.mjs` owns both the file set and the fingerprint, so never inline either in the workflow. The page is not part of the npm package and no product code may depend on it.
- **Panel controls float inside their band:** A control that belongs to a panel but not to its content flow (the inspector's fold tabs) floats within the panel's width, inset from its edges, over the content it scrolls with — never a row in the flow, never outside the panel's border, never a separate strip above it. A jumped-to section lands below the floating row (`scroll-margin-top`), so the way back is always in reach.
- **A block header names the block:** A section's caption says what the section is ("Artboards", "Elements"), not which item is selected — the selection is already lit in the list or tree it belongs to, and repeating its name costs the width a narrow panel needs. Detail about the current choice belongs on the row, in a tooltip, or in the empty state, never in the header.
- **One slot, one occupant:** When a host can do something another cannot, the control replaces the affordance it stands in for rather than stacking beside it — the composer's footer is either the key hints (a host that can only answer prompts) or the model/thinking selectors (a host that owns the session), never both. Pi users are assumed to know the shortcuts; the selectors carry their tips, and `?` still lists every key.
- **Entry points say what they are:** The root package's entry is the product library, and every other entry is a named subpath (`./runtime`, `./contract`, `./model`, `./boards`, `./plugins`, `./engine`, `./pi`). A host-specific manifest field at the root points at that host's **adapter entry** (`pi.extensions` → `dist/adapters/pi/index.js`), never at a root shim, and host-specific keywords belong to the host package. A folder-scanning host (Pi reads its extensions directory) is given the adapter **package** — a symlink to `adapters/pi`, which carries its own `pi.extensions` — so both install paths name one implementation. When adding a host, add a subpath and a thin packaging package; never grow the root into one host's shape.
- **Host capabilities are advertised, not assumed:** anything only one host can do (the Pi extension can change the session's model and thinking level; an MCP client cannot) is published as data in the board state (`agent.controls`), turned into a control when present and **absent** when not — never a disabled control, never a guessed value. The board stores no session setting as project content, asks only for values the host listed, and shows what the host reported applying. The host is the authority; the board is a view.
- **Scope discipline:** Preserve unrelated work. Do not publish, tag or deploy without explicit authorization.

## Interface rules

- **Chrome layout:** Islands stay in place: DIVLET button and search (top left, separate pills), the three tabs (bottom left, separate pills that join the sidebar when it opens) and the toolbar (bottom right) with the inspector attached above it. The sidebar (Layers / History of changes / Agent conversation) is one homogeneous surface: no horizontal border dividers, nested darker areas instead. Breadcrumbs sit bottom centre only (wrapping when narrow; sidebars cover them on phones). A tab both switches and, when already open, folds the sidebar.
- **Two homes, at most, for an action:** An action lives in at most two places, and one of them may be the index (command palette/search, shortcuts sheet). Closing the left sidebar is the active tab (or the `L`/`H` shortcut); there is no separate close button in the panel — the tabs are one row below it and a corner control only added a second way to do what a lit tab already says. When adding a control, name the two homes it takes and check that nothing else already offers it.
- **UX stability:** Errors, statuses and progress never move controls: messages render after the controls they concern, progress is drawn on the element that is working, action buttons keep a stable size.
- **Fluid layout:** A label and its control are one unit and wrap together, everywhere. Values (key caps, counts, times, tags) are as wide as their text and never wrap or squash. Prefer compact controls; test narrow widths (195px ≈ 200% on a phone).
- **Smart toolbars and units:** A toolbar fits itself: its actions sit in one row and whatever does not fit moves, in order, into a trailing dropdown built from the same list (`web/lib/toolbar.js`), never a hard-coded split. Chrome text is shown whole (it wraps; no ellipsis because a toolbar reached the screen edge). Numeric fields show their unit (px, %) beside plain numbers. The inspector is as wide as the toolbar under it by default and a double-click on its edge restores that.
- **Contracts are types:** A plugin or adapter boundary is an exported type, not a paragraph: `Importer`/`Exporter` in `core/lib/plugins.ts`, `StyleEngine` in `core/lib/engine.ts`, the capability schema and `Session` in `core/lib/contract.ts`. They are part of the package (`exports` entries `./plugins`, `./engine`, `./contract`, declarations emitted by the build) and must stay free of Node-only types so a plugin author can compile against them; `SourceBytes` is a `Uint8Array` for that reason. A JavaScript descriptor is glued in exactly one place per registry (`registerImporter`, `registerStyleEngine`, `registerExporter`), which is where the promise that it satisfies the contract is written down.
- **Prompt blocks, one grammar:** Anything the product injects into an agent's context is one compact block, in the shape the other extensions use: a bracketed English header with `|key:value` metadata, its value on the same line, lists from the next line in Markdown, then the payload after a blank line — `[divlet|project:<id>|frames:<n>|nodes:<n>] about “Pricing” with 1 element selected`, then `frames:` / `elements in <frame>:` / `next:`, then the user's request. Build board requests in `runtime.askMessage` (one place for Pi, MCP and anything later); a host may add its own per-turn context but not invent a second prose format.
- **Layers always has an artboard:** While the Layers pane is open, one artboard is chosen — the remembered one if it still exists, else the first — so the pane never shows an empty right-hand side next to a populated list; a project without artboards is the only case with nothing chosen. Enforce it where the pane renders (never in a general selection setter), so a canvas click or an Escape that clears the selection bounces back to the artboard the user had.
- **Icons:** One painted element per icon — a single `<path>` (a `<g>` only when one transform must apply to the whole glyph, as in the gear; a second element only when it is genuinely a different paint, as the filled half of `auto` and the dashed frame of `wrap`). Never put alpha on a part: opacity, `fill-opacity` and `stroke-opacity` belong to the icon element, so a crossing, a dot over stroke ends or a touching join cannot darken. Merge touching sub-shapes into that path instead of stacking elements.
- **No duplicated controls:** A control or function appears in at most two places: the general lists (shortcuts, command palette/search, agent tools) and the one place where it is most natural to use. Search for existing homes before adding one; move or merge rather than copy.

## Execution and validation

1. Read this file, the relevant docs and any affected entrypoint before changing code. Consult the backlog when selecting open work.
2. Trace the affected implementation, callers and tests. Prefer the smallest change at the owning boundary and a regression for the failure class.
3. Run the smallest decisive tests first (`node --test`, `npm run test:browser:all`, `npm run test:pi`); see the [testing guide](docs/testing.md). Documentation-only changes need link checks, not a rerun of unaffected suites.
4. Reconcile documentation and backlog state; keep completed work out of the backlog and describe unresolved limitations honestly.
5. Commit; report changed paths, checks actually run, remaining limitations and any external gate.

# divlet project context

divlet is a local browser layout board for agents. It edits validated static HTML/SVG/CSS projects, not arbitrary applications. Start with [README.md](README.md) for usage and [docs/README.md](docs/README.md) for technical documentation. The [web-native core contract](docs/web-native.md) owns the target semantics and plugin boundaries; [docs/format.md](docs/format.md) owns the wire-format specification and its explicit compatibility status.

## Meta-Protocol Principles

- **Constraint-driven structure:** Add context or abstraction only when it preserves a real constraint or makes an existing responsibility easier to find. Consolidate stale context rather than accumulating parallel instructions.
- **Durable rules:** This file owns contributor constraints and recurring engineering guidance, not task status or delivery history.
- **Open work:** [BACKLOG.md](BACKLOG.md) is the only task backlog. Keep only remaining, blocked or gated work there.
- **Completed changes:** [CHANGELOG.md](CHANGELOG.md) records implemented outcomes. Unreleased work must not be presented as a published release.
- **Human documentation:** README files are entrypoints; `docs/` owns architecture, operational guidance and the format reference ([docs/format.md](docs/format.md)).
- **Reconciliation:** When behavior or ownership changes, update its authoritative document, reconcile affected backlog items and record meaningful delivery. Do not duplicate the same status across files.
- **Git:** The repository is local. Commit after each coherent step.

## Topology

- **`core/` and `web/` are peers** (plugins can act on either). `core/` holds the server-side core (`core/index.js` entry, `core/lib/`, `core/tests/`); `web/` is the web client (`board.js` entry, `index.html`, `board.css`; its modules, one per domain, in `web/lib/`); `plugins/` and the adapter packages in `packages/` sit beside them.
- **Core:** Own one native model, its format/admission/projection and the local editor runtime. HTML admission is distinct from strict native decoding and managed-cache reconciliation; the browser owns layout and painting. Use the [current module map](docs/architecture.md#modules) for source locations and the [web-native contract](docs/web-native.md) for target semantics, not interchangeable plugin-defined document models.
- **Plugins:** Foreign formats use importer/exporter packages under `plugins/<id>/`; native HTML admission remains core-owned, bounded and non-overwriting. PEN interpretation must yield ordinary HTML/SVG/CSS without requiring a style engine. Tailwind owns its declaration/compiler and inspector capabilities, not the native model. Generic core layers depend on contracts, never concrete providers; select providers in composition code. Each plugin owns its dependencies in `package.json`, with a thin `index.js`, internals in `lib/` and tests in `tests/`. Client modules are served at `plugins/<id>/<file>` and import core client modules as `../../lib/<file>`. See the module map for current owners and the backlog for remaining composition gaps.
- **Adapters:** The real host packages in `packages/cli`, `packages/mcp` and `packages/pi` publish as `@divlet/cli`, `@divlet/mcp` and `@divlet/pi`; each owns its implementation and tests, with no wrapper layer. They consume public `divlet` and `divlet/contract`, never core internals or the reverse dependency; use the same entry/internal/test shape as plugins and start no service at import time. They translate the shared capability contract rather than re-implement operations. Their versions match the root product release and their `divlet` dependency is exact. The root library stays harness-agnostic. The portable workflow in `skills/divlet/` belongs to the product, not a host.
- **Agent workflow:** `skills/divlet/` belongs to the product, not to an adapter: it is the portable workflow an agent loads (Pi finds it through the extension; other hosts install it globally). It is the product's **entry point**, written for an agent that has nothing else: install the tools (an MCP host registers `npx -y @divlet/mcp`), open a project, then follow the loop. Keep it a walkthrough, not a reference dump — every claim it makes must be true of the code, and `core/tests/skill.test.js` enforces exactly that (tool names, CLI flags, error codes, documents, front-matter limits). It is distinct from this contributor guide.
- **Tests:** `core/tests/` owns server/model unit tests; `web/tests/` owns frontend unit and browser acceptance suites. Frontend tests are neither served client modules nor publishable assets; build copying and module-graph checks must exclude them. Shared core fixture builders stay in `core/tests/fixtures/`. The Pi RPC scenario and its mock provider live with their adapter in `packages/pi/tests/e2e/pi.mjs`, plugin tests in `plugins/<id>/tests/`. See [testing](docs/testing.md). Generated screenshots belong in the ignored `artifacts/` directory.

## Operating Principles

- **Language and identity:** Write project documentation and code comments in English. Keep the public identity `divlet`, the `/divlet` command and `*_divlet` tools. Tool contracts use `frames` and `frameId`; internal code may use `document` and `documentId`.
- **Format direction:** Follow the [web-native core contract](docs/web-native.md): HTML/SVG/CSS is native; Tailwind is an optional representation/compiler/UI plugin, even when enabled by default. Class names are ordinary HTML classes and tokens are CSS variables. Plain-CSS creation, editing and rendering must not require a style engine. Keep structural fields explicit and metadata extensible within the safe JSON profile; shared semantics should have one validator rather than context-specific copies. This is the target direction, not a claim that every current path already conforms; remaining implementation work belongs in [BACKLOG.md](BACKLOG.md).
- **Native HTML, plugins for foreign formats:** External HTML admission belongs in the core and stays distinct from strict native decoding, reverse-cache reconciliation and clean export. A foreign format is an importer plugin. Never name a foreign format in the core, and never edit a foreign source in place: it is converted once into a sibling `.divlet` (an existing `.divlet` is never overwritten, an unconvertible source opens as itself with diagnostics). Imported bytes are never rewritten; the one exception is a legacy `.divlet` that still holds a foreign source — its bytes are moved to a free `<name>.pen` and the `.divlet` path becomes the converted project.
- **Initial schema marker:** Native project and standalone-frame envelopes remain `schemaVersion: 1` until the first format freeze. Unpublished draft iterations do not establish schema generations 2/3; do not introduce another draft-version discriminator or numbering-only migration instead. Keep npm versions and content revisions separate, preserve strict validation and never rewrite opaque metadata or foreign-format versions as part of numbering.
- **Source ownership:** Each `<name>.divlet` file is canonical and independently identified by its full path. Default creation is `project.divlet` in the chosen directory, without a wrapper folder. Preserve hand edits rather than silently overwriting them.
- **Editor state is not content:** Selection, hover, tools, viewport navigation, panel preferences and measured element geometry address the model but do not become project content by default or advance its content revision. Authored artboard geometry is content. Keep internal IDs, DOM IDs and instance occurrence addresses distinct. User-set panel widths are primary local preferences: defaults/toolbar following apply only without a valid preference; viewport/scale constraints must never overwrite it and cancelled resizing must not commit. Reset is explicit. Browser storage is origin-scoped (including the port), not cross-launch storage by itself.
- **Managed projection:** The target HTML/CSS cache is a rebuildable, reverse-editable projection, not a second source of truth. Reverse edits must preserve identity, component meaning, resource provenance and authored-versus-generated CSS, and reject stale or ambiguous candidates through the same acceptance path as tools and JSON edits. Clean static export is a separate contract; do not claim the editing round trip is implemented merely because HTML can be decoded.
- **Style transformations:** Core style edits must have a plain-CSS path. Optional normalization must be explicit, idempotent and cascade-preserving, reconciling superseded inline declarations and utilities. Retain ordinary CSS when equivalence is unproven. Missing required plugins must be diagnosed; disabling a dependent engine must preserve styling through a validated conversion or refuse, never silently drop compiled CSS.
- **Output ownership:** `core/lib/output.ts` owns generated-file provenance, collision checks and symbolic-link refusal. Never overwrite unowned output paths or share one output directory between projects. Generated files belong in `.divlet/<name>/` (or the project's relative `outputDir`). Keep the public static graph distinct from the complete disk-publication/repair plan: editor sidecars must remain repairable without becoming HTTP-served public files.
- **Local filesystem model:** Projects may live and be edited anywhere permitted by the OS; referenced local resources resolve automatically, including absolute paths. Keep bounded regular-file reads, no-link checks and non-overwriting publication. This is trusted local-project access, not an arbitrary HTTP filesystem route.
- **Portable semantic slices:** Browser extraction shares admission/operation code with Node rather than duplicating validators or hiding host dependencies behind blanket polyfills. Keep Node built-ins and concrete provider bootstrap outside a declared portable slice; preserve existing standalone provider defaults and the connected host's writer authority. Prove browser operations with real browser imports, not TypeScript compilation alone. See [browser runtime boundaries](docs/browser-runtime.md).
- **Validated commits:** Check the expected version, prepare and validate the candidate before changing accepted state, and retain the last working state on invalid external edits. Do not bypass these rules in HTTP handlers or Pi tools.
- **History safety:** Undo/redo must validate a whole group or requested multi-step traversal before committing it and refuse overlapping later edits without changing state. Move stack authority only after the full candidate persists; never implement history navigation as a browser loop of independently accepted Undo calls. Frame order is authored state: lifecycle replay restores original slots, and reorder replay checks its expected relative order without rearranging unrelated later frames. State-point IDs name proven stack endpoints, not audit sequence numbers: invalidate extended group frontiers and expose nonlinear/untracked boundaries without destroying legacy Undo/Redo. Check a navigation request's expected point inside the writer queue and advance point authority with the committed stacks.
- **Preview trust:** A matching iframe `WindowProxy` is not authentication after navigation. Keep model, selection and editing traffic on the authenticated document-bound MessagePort; keep referrer protection and capability rotation on preview reset, and retire the editor port/capability before entering a separate read-only browsing document.
- **Serialized bridge code:** Editor, site and read-only browsing helpers injected through `Function#toString` must stay free of imports and outer-scope dependencies.
- **Local HTTP boundary:** Preserve loopback binding, token-scoped routes, Host/Origin checks, CSP, request-size bounds and filesystem confinement.
- **One writer per project:** A board owns its project file and is the only writer. Clients (browser, Pi, MCP, CLI) attach to the board found in `core/lib/boards.ts`; do not open a second runtime for a project another live board owns. Attached traffic uses the board's token-scoped `api/tool` route, which runs the same contract.
- **Long-lived frames:** Each artboard keeps one iframe for the project's lifetime, loaded lazily by the browser (`loading="lazy"`, eager only for selected/expanded frames). Do not reintroduce scroll/zoom-driven unmounting; swap a frame only behind a ghost of its previous page. At far zoom a cached PNG may stand in for the live page.
- **TypeScript:** The product is TypeScript. Migrated sources are `.ts`. The browser remains native JavaScript ES modules pending its typing strategy; current `tsconfig.json` excludes `web/` and sets `checkJs: false`, so the TypeScript gate is not evidence of full JavaScript/client checking. Node runs the sources directly by stripping types — there is no build in the development loop — so a file's own imports name the real file (`./model.ts`), the compiler is configured `strict` with `erasableSyntaxOnly` (no enums, namespaces, parameter properties, decorators), and `npm test` starts with `npm run typecheck` (strict Node/core plus the scoped DOM-only client profile); `tsconfig.web.json` owns the checked browser subset, not a full-client checking claim. `dist/` is generated by `npm run build` for publishing only: never edit it, never commit it. Vocabulary belongs in `core/lib/model.ts`; a module types its own boundary and treats foreign input as `unknown` until the validator accepts it.
- **Embedded-resource target:** Project-owned file-asset bytes belong in the native `.divlet`, with only disposable materialization under `.divlet/<project>/assets/` beside generated pages. A canonical sibling `assets/` folder or a cache-only copy is not the target. The declared hierarchical `assets` tree owns reusable names/paths; explicit references materialize those files, while literal Data URLs at use sites remain inline. Never automatically extract inline URLs or rename declared keys merely to deduplicate bytes. Implement storage/reference validation, byte budgets and all resource consumers coherently before claiming this capability; preserve existing resources until conversion retains their bytes. Preserve the existing bounded local-resource import model; resource identifiers never authorize executable content or unrequested network fetches.
- **Public demo data:** Never use `runtime.info()` as a public snapshot template: it includes private paths and session/editor state. Project inspection data only from explicitly curated public prepared content, with an allowlisted state shape and deliberate presentation geometry. Keep prepared HTML as rendering authority; metadata omission/model validity do not establish provenance, content secrecy, reference closure or whole-UI read-only enforcement.
- **One authored landing:** Each example owns its folder. The canonical English onboarding/demo source belongs at `examples/landing/landing.divlet`; its `index` frame generates `examples/landing/.divlet/landing/index.html`. Keep identity, commands and release status consistent with the root README. Do not maintain a second hand-authored HTML site or marketing tree in core code. Other bundled examples may remain importer/site/layout scenarios, not duplicate landing sources. Any composition that seeds workspaces from this template must create an independently owned validated copy, never edit the installed master; explicit paths and no-demo creation remain authoritative.
- **The landing build is derived, tracked and selectively published:** the named `examples/landing/.divlet/landing/` build is an explicit exception to ignoring generated project output, not permission to hand-edit it or commit arbitrary caches. Regenerate through normal validation and output ownership; a fresh checkout must rebuild safely, with portable provenance where required. Never track locks, recovery trash or session capabilities. CI publishes the prepared portable HTML/CSS/resource set to the `gh-pages` root, not a raw cache-directory copy: sidecars, ownership metadata, trash and editor/private payloads are not public artifacts. `scripts/landing-hash.mjs` owns both the published file set and its fingerprint; unchanged public bytes mean no deployment commit. Check source/build freshness in a relocated sandbox, preserve self-contained rendering and relative URLs, and do not mistake this architecture for authorization to push or deploy. Keep the canonical source/assets in the npm example payload, but exclude this cache; the Pages public set adds only its required `.nojekyll` marker and fingerprint record, not editor metadata.
- **The inspector is one vertical flow:** Section summaries are the only section-navigation controls; do not duplicate them in horizontal tabs, floating jump bars or reorder strips. Keep sections in their owning panels' stable order and remember open/closed state as a local preference, not project content. The read-only measured X/Y/W/H and overflow block is the final section, after metadata. Use native keyboard-accessible disclosure controls, unobstructed vertical scrolling and whole label/control units that reflow at narrow widths; minimal chrome must not remove access to properties.
- **A block header names the block:** A section's caption says what the section is ("Artboards", "Elements"), not which item is selected — the selection is already lit in the list or tree it belongs to, and repeating its name costs the width a narrow panel needs. Detail about the current choice belongs on the row, in a tooltip, or in the empty state, never in the header.
- **One slot, one occupant:** When a host can do something another cannot, the control replaces the affordance it stands in for rather than stacking beside it — the composer's footer is either the key hints (a host that can only answer prompts) or the model/thinking selectors (a host that owns the session), never both. Pi users are assumed to know the shortcuts; the selectors carry their tips, and `?` still lists every key. Send remains the footer's bottom-right action when either occupant wraps: use its own auto margin and bottom alignment, not a preceding flex spacer.
- **Entry points say what they are:** The root package's entry is the product library, with named public subpaths such as `./runtime`, `./contract`, `./model`, `./boards`, `./plugins`, `./engine` and the shared `./skill` resource. It has no bins, Pi manifest/peer requirements or `./pi` export. Each adapter package owns its `dist/index.js` entry, exports and relevant bin or `pi.extensions`; host-specific keywords and dependencies stay there. A folder-scanning Pi installation targets the built `packages/pi` package, never the repository root. Source execution uses the `divlet-source` export condition; `scripts/source.mjs` propagates it through `NODE_OPTIONS` to children. The npm workspace includes `.`, `packages/*` and `plugins/*`. Development runs sources; `dist/` is publishing output only.
- **Host capabilities are advertised, not assumed:** anything only one host can do (the Pi extension can change the session's model and thinking level; an MCP client cannot) is published as data in the board state (`agent.controls`), turned into a control when present and **absent** when not — never a disabled control, never a guessed value. The board stores no session setting as project content, asks only for values the host listed, and shows what the host reported applying. The host is the authority; the board is a view.
- **Scope discipline:** Preserve unrelated work. Do not publish, tag or deploy without explicit authorization.

## Interface rules

- **Chrome layout:** Islands stay in place: DIVLET button and search (top left, separate pills), the three tabs (bottom left, separate pills that join the sidebar when it opens) and the toolbar (bottom right) with the inspector attached above it. The sidebar (Layers / History of changes / Agent conversation) is one homogeneous surface: no horizontal border dividers, nested darker areas instead. Breadcrumbs sit bottom centre only (wrapping when narrow; sidebars cover them on phones). A tab both switches and, when already open, folds the sidebar. Tab density follows the tab row's own width, not pane visibility: narrow tabs place the icon/count above the whole label within their unchanged height; folding must not reset that layout. The composer's context header has intrinsic height and a real gap before the input, including when it wraps.
- **Two homes, at most, for an action:** Keep one natural control location plus the general indexes (shortcuts, command palette/search, agent tools), never duplicated interface controls. Before adding one, name its homes and search for existing affordances; move or merge rather than copy. Closing the left sidebar is the active tab (or `L`/`H`), not a separate panel/corner close button.
- **UX stability:** Errors, statuses and progress never move controls: messages render after the controls they concern, progress is drawn on the element that is working, action buttons keep a stable size. The Agent activity plaque is a five-column, three-row grid: indicator at the start, activity text across the upper rows, time in the footer and Stop in the bottom-right cell; do not squeeze them back into one flex row. While busy and the entire left sidebar is folded, move that same plaque above the tabs at the remembered sidebar width, never clone it or add a second Stop. In this floating form, put the spinner in the bottom-left cell, vertically centred with the timer and Stop in the footer, and let the description span the full width above; the open-panel indicator stays in its original upper cell. Tabs stay put; long floating activity scrolls inside its bounded text area, and phone sheets clear the measured footer. Idle and expanded browsing show no floating plaque.
- **Chat stacks by the composer:** Keep chronological DOM order and bottom-align spare space with an auto margin, never a reversed column or overflowing `flex-end`. Only the conversation scrolls once full. Follow arrivals and layout resizing while near the bottom; preserve an older reading position and explicit message focus.
- **Fluid layout:** A label and its control are one unit and wrap together, everywhere. Values (key caps, counts, times, tags) are as wide as their text and never wrap or squash. Numeric fields need room for their actual/default text, not merely an overflow-free wrapper around a zero-width input. Let control grids respond to their available width instead of forcing a phone column count. Match minimums to content, not one blanket floor: short bounded fields such as radius/border stay paired even in a narrow inspector, while longer selectors wrap without clipping. Prefer compact controls; test narrow widths (195px ≈ 200% on a phone).
- **Box-model editing stays direct:** Use nested position → margin → border → padding bands with full layer names and measured content dimensions at the centre. Keep exactly eight independent margin/padding fields, native label targets and single-side highlighting; no linking modes or duplicate editors. Positioned offsets belong only to the outer band; per-side border readouts are measured, while Appearance owns width editing. Bands are schematic; preserve signed/fractional values, use `—` for unavailable measurements and give long values room instead of clipping.
- **Smart toolbars and units:** A toolbar fits itself: its actions sit in one row and whatever does not fit moves, in order, into a trailing dropdown built from the same list (`web/lib/toolbar.js`), never a hard-coded split. Chrome text is shown whole (it wraps; no ellipsis because a toolbar reached the screen edge). Tooltip copy and headings wrap, including unbroken references; cap their width to the scaled viewport and place them using their measured multiline size. Numeric fields show their unit (px, %) beside plain numbers. Dropdown labels and values are vertically centred, with labels carrying stronger contrast than values. The inspector is as wide as the toolbar under it by default and a double-click on its edge restores that.
- **Contracts are types:** A plugin or adapter boundary is an exported type, not a paragraph: `Importer`/`Exporter` in `core/lib/plugins.ts`, `StyleEngine` in `core/lib/engine.ts`, the capability schema and agent-host `Session` in `core/lib/contract.ts`, and the board's transport-free `BoardReadSession` in `core/lib/board-session.ts`. The public plugin/agent contracts ship through `./plugins`, `./engine` and `./contract` with emitted declarations; the internal board read port has no public subpath yet. All these contracts must stay free of Node-only types so a plugin author can compile against them; `SourceBytes` is a `Uint8Array` for that reason. A JavaScript descriptor is glued in exactly one place per registry (`registerImporter`, `registerStyleEngine`, `registerExporter`), which is where the promise that it satisfies the contract is written down.
- **Prompt blocks, one grammar:** Anything the product injects into an agent's context is one compact block, in the shape the other extensions use: a bracketed English header with `|key:value` metadata, its value on the same line, lists from the next line in Markdown, then the payload after a blank line — `[divlet|project:<id>|frames:<n>|nodes:<n>] about “Pricing” with 1 element selected`, then `frames:` / `elements in <frame>:` / `next:`, then the user's request. Build board requests in `runtime.askMessage` (one place for Pi, MCP and anything later); a host may add its own per-turn context but not invent a second prose format.
- **Layers always has an artboard:** While the Layers pane is open, one artboard is chosen — the remembered one if it still exists, else the first — so the pane never shows an empty right-hand side next to a populated list; a project without artboards is the only case with nothing chosen. Enforce it where the pane renders (never in a general selection setter), so a canvas click or an Escape that clears the selection bounces back to the artboard the user had.
- **Icons:** One painted element per icon — a single `<path>` (a `<g>` only when one transform must apply to the whole glyph, as in the gear; a second element only when it is genuinely a different paint, as the filled half of `auto`, the dashed frame of `wrap`, or the logo's outlined bracket and filled D). Never put alpha on a part: opacity, `fill-opacity` and `stroke-opacity` belong to the icon element, so a crossing, a dot over stroke ends or a touching join cannot darken. Merge touching sub-shapes into that path instead of stacking elements.

## Execution and validation

1. Read this file, the relevant docs and any affected entrypoint before changing code. Consult the backlog when selecting open work.
2. Trace the affected implementation, callers and tests. Prefer the smallest change at the owning boundary and a regression for the failure class.
3. Run the smallest decisive tests first (`node scripts/source.mjs --test …`, `npm run test:browser:all`, `npm run test:pi`); see the [testing guide](docs/testing.md). Documentation-only changes need source link checks; when shipped links change, also run `node scripts/source.mjs --test core/tests/package.test.js` for the packed documentation graph, not unrelated runtime/browser suites.
4. Reconcile documentation and backlog state; keep completed work out of the backlog and describe unresolved limitations honestly.
5. Commit; report changed paths, checks actually run, remaining limitations and any external gate.

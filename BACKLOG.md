### Native CSS and optional providers

Checkpoint: a plain HTML/CSS project can be created, edited and rebuilt without a style engine; optional normalization preserves the requested CSS semantics and dependent projects cannot silently lose styling. Native HTML input is part of this stabilization gate: retain `core/tests/html-import.test.js` coverage for registry-independent admission, source preservation, listing policy and guarded re-import while implementing the remaining provider work.

- [ ] **WEB-1 — Give semantic style edits a native CSS path.** `styles` currently delegates to the active engine and throws `NO_STYLE_ENGINE` without one. With Tailwind, a pre-existing inline declaration can still win over the new utility (request 16px padding, retain 12px inline, render 12px). Separately, `codec.layered` wraps authored CSS in the components layer even without an engine: a blue token beats a later authored red `:root` declaration, unlike native CSS. Reordering `style` members `padding-left:20px`/`padding:10px` also changes Chromium's left padding from 10px to 20px while current deep comparison considers the models equal. Implement the approved native emission and ordered declarations through FORMAT-TRANSITION; these persisted-meaning sub-boundaries are not merely editor features. Make the owning style operation reconcile both representations, retain unrelated declarations and preserve states/variants. Verify `core/tests/model.test.js`, `core/tests/no-engine.test.js` and a browser witness for an imported inline-styled element; cover enabled/disabled engines and repeated normalization.
- [ ] **WEB-2 — Separate plugin composition and PEN conversion from native semantics.** Move concrete provider selection out of generic model/registry loading; the current engine and importer registries import built-ins directly. Make PEN conversion produce ordinary HTML/SVG/CSS without requiring `declarationClass`; optional normalization runs after conversion. Verify native loading without optional providers, styled PEN conversion with no engine, and explicit default-plugin composition through `core/tests/html-import.test.js`, `core/tests/no-engine.test.js`, `core/tests/entrypoints.test.js` and `plugins/pen/tests/convert.test.js`.
- [ ] **WEB-3 — Define and enforce rendering dependencies and engine disable semantics.** The current project schema has no enforced dependency profile, and compiling utilities with no engine yields an empty stylesheet. First resolve release dependency reproducibility: local source/build tokens agree, but a clean tarball installation produced a different effective token. Trace the selected inputs and pin the intended release closure before freezing; do not weaken exact matching or silently rewrite requirements. Then integrate the opt-in versioned compiler descriptor through trusted host composition and the approved project `requires` representation, not a default-engine or class-name guess. Bind resource/inspector capabilities to the same effective provider before claiming complete project support; the current versioned descriptor is compiler-only. Retain draft helper/ambient-base behavior until cutover and add explicit migration rules. Diagnose missing required providers without guessing from classes. Disabling a dependent engine must materialize equivalent ordinary CSS through the accepted-state path or refuse without changing the project. Verify rebuild after deleting cache, missing-provider diagnostics, successful conversion and refused conversion with retained source/history/output in the no-engine and output suites plus a computed-style browser check.

Treat `bridge.js` last and differently: its browser function is serialized with `Function#toString`, so prefer a typed wrapper around an unchanged self-contained body and convert only when the cost is justified. - [ ] **BROWSER CLIENT — Type `web/` and keep the board served without a bundler.** The client is plain ES modules served as files, so it cannot be shipped as `.ts`: either compile `web/` to `dist/web` (the build already mirrors assets there) and serve the built copy in the installed package while developing against sources, or type it with `checkJs` + JSDoc `@import` from `core/lib/model.ts`. - [ ] **SKILL-A11Y — Read the skill as its own reader would.** The skill is now the entry point (2026-11-12) and is checked against the code, but nobody has measured whether an agent that has *only* the skill actually succeeds: the honest check is a run in a host with no divlet extension (register `divlet-mcp`, load the skill, ask for one change) and a note of where it hesitated. Suspects: the install section assumes the host can start a subprocess; the loop says "verify" without saying what a good `view:preview` answer looks like.
- [ ] **PI-ONLY FEATURES — Keep going where only the extension can reach.** The first one landed (2026-11-12): the Agent pane's model and thinking-level chips, advertised through `agent.controls`, applied by Pi, never stored in the project. Do not add a control without naming what the host does with it and what the board shows if the host refuses.

## P2 — hardening

- [ ] **MCP REGISTRY — Scope the board registry to the user who owns it.** `core/lib/boards.ts` stores each board as a file in `~/.divlet/boards/` (`0600` in a `0700` directory) holding the board URL, which carries its access token — i.e. full access to that board's local API. On a machine where several accounts share a home directory (or `PI_DIVLET_STATE_DIR` points at a shared path) one account could attach to another's board. Compare the entry's owner uid with `process.getuid()` on read, or move the registry to a per-uid unix socket, and keep the stale-owner cleanup. Deliberately deferred: single-user local machines are the supported case today.

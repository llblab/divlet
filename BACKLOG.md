## P1 — format freeze preparation

Prepare the first-release specification candidate in [docs/format.md](docs/format.md), with executable evidence and a precise freeze assessment. The preparation scope does not authorize schema changes, declaring stability, publishing, tagging or deployment. Stop when the candidate, baseline evidence and attributed blockers are ready; implementation/release work needs its own scope.

Checkpoint: accepted/rejected examples and semantic read/write expectations support the candidate; every unresolved persisted-semantics decision has a named owner and unblocker, without making all editor work a format-freeze prerequisite.

- [ ] **FORMAT-EVIDENCE — Establish a portable conformance baseline and reader-boundary witnesses.** Reuse the model/project/codec validators rather than introducing a competing schema. Add plain JSON examples for supported project/frame/node/component forms and rejected classes, verify defaults and semantic read/write stability, and validate the specification's complete JSON example. Audit project-versus-frame name/metadata validation, null/default rules, unknown/future fields and numeric representability; record counterexamples as blockers, not compatibility guarantees. Use a focused `core/tests/format.test.js` family with portable data under `core/tests/fixtures/format/`; distinguish baseline coverage from full conformance.
- [ ] **FORMAT-ASSESS — Review the candidate against its evidence and classify freeze gates.** Check field/default coverage, version/revision distinctions, supported HTML/SVG/CSS, resource/identity semantics and compatibility claims. Attribute persisted rendering-dependency decisions to WEB-3 and component/override/DOM-ID decisions to WEB-4; identify whether WEB-1/WEB-2/WEB-5 require a saved-model change or only implementation. Record concrete recommendations and remaining approval/implementation gates in the format reference, with no duplicate work list. Verify every reported blocker against code or a reproducible witness and reconcile this checkpoint.
- [ ] **FORMAT-FREEZE — Approval-gated: accept the final format and compatibility policy.** After preparation, resolve the reported reader/compatibility and WEB-3/WEB-4 persisted-semantics blockers, update their implementation/conformance evidence and obtain explicit approval for the exact candidate. Only then replace candidate status with a frozen declaration. npm publication remains a separate gate in [docs/publishing.md](docs/publishing.md).

### Native CSS and optional providers

Checkpoint: a plain HTML/CSS project can be created, edited and rebuilt without a style engine; optional normalization preserves the requested CSS semantics and dependent projects cannot silently lose styling. Native HTML input is part of this stabilization gate: retain `core/tests/html-import.test.js` coverage for registry-independent admission, source preservation, listing policy and guarded re-import while implementing the remaining provider work.

- [ ] **WEB-1 — Give semantic style edits a native CSS path.** `styles` currently delegates to the active engine and throws `NO_STYLE_ENGINE` without one. With Tailwind, a pre-existing inline declaration can still win over the new utility (request 16px padding, retain 12px inline, render 12px). Make the owning style operation reconcile both representations, retain unrelated declarations and preserve states/variants. Verify `core/tests/model.test.js`, `core/tests/no-engine.test.js` and a browser witness for an imported inline-styled element; cover enabled/disabled engines and repeated normalization.
- [ ] **WEB-2 — Separate plugin composition and PEN conversion from native semantics.** Move concrete provider selection out of generic model/registry loading; the current engine and importer registries import built-ins directly. Make PEN conversion produce ordinary HTML/SVG/CSS without requiring `declarationClass`; optional normalization runs after conversion. Verify native loading without optional providers, styled PEN conversion with no engine, and explicit default-plugin composition through `core/tests/html-import.test.js`, `core/tests/no-engine.test.js`, `core/tests/entrypoints.test.js` and `plugins/pen/tests/convert.test.js`.
- [ ] **WEB-3 — Define and enforce rendering dependencies and engine disable semantics.** The current project schema has no enforced dependency profile, and compiling utilities with no engine yields an empty stylesheet. Choose compatible dependency/version representation and migration rules; diagnose missing required providers. Disabling a dependent engine must materialize equivalent ordinary CSS through the accepted-state path or refuse without changing the project. Verify rebuild after deleting cache, missing-provider diagnostics, successful conversion and refused conversion with retained source/history/output in the no-engine and output suites plus a computed-style browser check.

### Reversible projection and identity

Checkpoint: managed HTML edits map back to the correct native objects through guarded acceptance, without order-dependent overrides, accidental component detachment, resource rebasing or compiled-CSS duplication. Clean static export remains independently usable.

- [ ] **WEB-4 — Finish component identity and override semantics.** Reject overlapping writes or define explicit precedence independent of JSON member order; `button.text` and its text child's `content` currently produce different results when their keys are reordered. Specify component CSS/token scope and prevent ambiguous repeated DOM IDs, including references such as `for`, ARIA ID lists and SVG fragments. Preserve valid instance selection/provenance across re-rendering. Verify `core/tests/components.test.js`, `core/tests/codec.test.js` and a browser reference/selection witness.
- [ ] **WEB-5 — Implement guarded reverse editing of managed HTML.** `scanOutputs()` currently diagnoses edited generated pages without importing them. First define the reversible projection/provenance for text IDs, nested instance addresses, resource rewrites and authored-versus-compiled CSS; do not substitute native external-HTML admission or clean export for that contract. Then admit expressible edits through the same validated writer/history path as tools and JSON, refuse ambiguous structural or stale edits while retaining authored bytes, and suppress own-write import loops. Build on WEB-4 identity and WEB-1 style semantics. Verify codec/component/runtime suites and `core/tests/browser/run.mjs` for valid, invalid, conflicting and component-instance edits, plus retained clean static output.

## P1 — product

- [ ] **KEY FORWARDING — A key pressed during a focus transition is lost.** Two symptoms, one class: (a) `features.mjs` "Enter in a list item saves it and starts a new one" fails in roughly one run of three inside `npm run test:browser:all` and passes standalone — the text typed into the second list item never reaches the model, so the later `Enter` has nothing to save; (b) `controls.mjs` "rename with `R` and by double-clicking the label" timed out once in a battery run (`.ab-rename` never appeared after `R`) and passed 5/5 standalone. Nothing is written to the project in either case, so this is a protocol/timing weakness rather than data loss, but a user pressing a shortcut right after clicking a panel would see the same dropped key. Suspect the ordered key channel (keys sent to the frame before the editor exists, and canvas shortcuts arriving while the previous focus owner still has it). Next step: capture the frame's key channel, the selected node, `document.activeElement` and the editor's lifetime around a failure; then make the hand-off explicit (the board confirms the editor is ready before forwarding, or buffers keys for the target) instead of adding waits in tests.

- [ ] **INSPECTOR SECTIONS — Work through each section's layout, not just its controls.** The spacing box model is settled (nested, always, 2026-11-12). Remaining is the rest of the inspector: every section (Layout, Effects, Appearance, type, size, colour, tokens) deserves the same treatment — what belongs in one row, what pairs into two columns when the panel is wide, what collapses to one column when it is narrow, and which controls earn their place at all. The adaptive hook exists (`.grid2` flows by available width, the box model uses container queries); the work is deciding each section's shape rather than adding another generic breakpoint.

- [ ] **INSPECTOR FOLD ORDER — Decide where the order lives.** The fold tabs are done (2026-11-10): one tab per fold above the inspector, a click opens and scrolls to that fold, dragging a tab reorders the folds with a mouse **or a finger** (pointer events, `touch-action: none`), `Alt + ← →` does the same from the keyboard, only the folds move so the class editor and the other sections keep their slots, and the order is remembered in `localStorage` (`divlet:inspector-order`). Remaining: decide whether the order should travel with the project instead of with the user — a project-level order means a settings field (patched with `expectedVersion`), a version bump and a documented format field, so it is a format decision rather than a UI one.

- [ ] **TAB BRIDGE — Let the open tab belong to its panel.** With a panel open its tab could read as that panel's own header (the active tab's surface continuing into the panel, the other two inactive) instead of all three sitting on one solid bar. Today the bar is solid and the active tab is tinted (`--accent-soft`); this is a refinement of that chrome language, paired with the `data-panels` rule.

Remaining, in this order — each step keeps `node --test`, the browser suites, `test:mcp`, `test:contract`, `test:pi` and `test:release` green:

- [ ] **CORE TYPES — Convert `core/lib/` module by module, boundary first.** Done (2026-11-12): `model`, `engine`, `project`, `codec`, `render`, `ops`, `diff`, `boards`, `plugins`, `import`, `launch`, `projects`, `hub`, `output`, `server`, `site` — 16 of 20 modules, every suite green at each step. Done since: `contract` (2026-11-12) — the surface plugins and adapters consume — plus the exported type entries (`divlet/plugins`, `divlet/engine`, `divlet/contract`) and a release check that compiles a plugin author's file against the installed declarations. Remaining, in this order: `static` (the build: `buildStatic` — real Node data flow, worth typing), `runtime` (the board: the largest; `server.ts` already extends the contract's `BoardRuntime`, so converting the runtime replaces that hand-declared shape with the real one), and `bridge` **last and differently**: it is one browser function serialized with `Function#toString` into the preview page, so it crosses no type boundary — convert it only if the cost is justified, and prefer a typed wrapper around an unchanged body over annotating forty browser globals. `engine.js` (the style-engine seam: type the `StyleEngine` interface and the `through` fallback so plugin engines stay checked), `project.js`, `codec.js` + `render.js`, `ops.js`, `diff.js`, `history` in `runtime.js`, then `boards.js`, `server.js`, `bridge.js`, `static.js`, `site.js`, `output.js`, `projects.js`, `hub.js`, `launch.js`, `plugins.js`, `import.js`, and finally `runtime.js` and `contract.js` (both large; `contract.ts` should export the parameter and result types the adapters render). - [ ] **BROWSER CLIENT — Type `web/` and keep the board served without a bundler.** The client is plain ES modules served as files, so it cannot be shipped as `.ts`: either compile `web/` to `dist/web` (the build already mirrors assets there) and serve the built copy in the installed package while developing against sources, or type it with `checkJs` + JSDoc `@import` from `core/lib/model.ts`. - [ ] **SKILL-A11Y — Read the skill as its own reader would.** The skill is now the entry point (2026-11-12) and is checked against the code, but nobody has measured whether an agent that has *only* the skill actually succeeds: the honest check is a run in a host with no divlet extension (register `divlet-mcp`, load the skill, ask for one change) and a note of where it hesitated. Suspects: the install section assumes the host can start a subprocess; the loop says "verify" without saying what a good `view:preview` answer looks like.

- [ ] **PI-ONLY FEATURES — Keep going where only the extension can reach.** The first one landed (2026-11-12): the Agent pane's model and thinking-level chips, advertised through `agent.controls`, applied by Pi, never stored in the project. Do not add a control without naming what the host does with it and what the board shows if the host refuses.

## P2 — hardening

- [ ] **MCP REGISTRY — Scope the board registry to the user who owns it.** `core/lib/boards.js` stores each board as a file in `~/.divlet/boards/` (`0600` in a `0700` directory) holding the board URL, which carries its access token — i.e. full access to that board's local API. On a machine where several accounts share a home directory (or `PI_DIVLET_STATE_DIR` points at a shared path) one account could attach to another's board. Compare the entry's owner uid with `process.getuid()` on read, or move the registry to a per-uid unix socket, and keep the stale-owner cleanup. Deliberately deferred: single-user local machines are the supported case today.

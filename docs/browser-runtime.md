# Browser runtime, offline demo and agent connectivity

**Status: incremental implementation, not a completed offline editor or a frozen API.** Shared standalone-frame validation, ordinary patches and inspection execute in native browser ESM as well as Node. A browser-local whole-project writer (`core/lib/browser-runtime.ts`: frames, components, structural edits, frame lifecycle, guarded Undo/Redo, work marks) now runs the shared contract tools with Node parity vectors, and the real board runs on it as a static site — the GitHub Pages board, which is also its own MCP provider ([browser-hosted MCP](browser-mcp.md)). Embedded asset bytes, fonts, sites, utility compilation, offline reload and multi-tab ownership still require the Node host or remain open. This note separates the portable semantic kernel direction, static-hosted demo and browser-agent transports. Implementation proceeds through bounded validated slices, not a wholesale runtime rewrite or a new release prerequisite. [BACKLOG.md](../BACKLOG.md) owns remaining work. The [web-native contract](web-native.md) remains the semantic authority.

## Current evidence

- Generated project pages already work on ordinary static hosting. That does not mean the editor can run without its host.
- Board bootstrap, state/change subscriptions and cached frame reads use `BoardReadSession`; writes, previews, exports and component lists use `BoardWriter`, `BoardPreviews`, `BoardExports` and `BoardComponents`. `web/lib/host.js` composes the native HTTP/SSE adapters, or a complete `BoardHostComposition` published before startup (the static browser host), with no fallback to native routes. Native-only affordances (open/save-as, build output, image/font upload, the board conversation) are absent in the browser host by `native`/capability checks, not disabled.
- `core/lib/validation.ts` owns shared domain errors, JSON/object/key/text checks and bounded UTF-8 budget admission without runtime imports or Node globals. Existing model-facing error/function identities remain shared.
- `core/lib/asset-reference.ts` shares portable declared-name/path checks with the Node byte decoder and implements the explicit `asset:` URI codec and bounded relative dependency resolution. Native-browser ESM runs the same reference witnesses without bundling or import rewriting. The frame model also uses that codec for resource-only attributes, including head icons and SVG `use`, with shared navigation/form/context refusals and tag-change safety. Controlled native-frame preparation followed by declared closure proves real image/SVG-use loading under a prefix. The Node writer now admits and projects the project asset tree, but that decoder still needs its Node host; this is not browser-local project storage or font upload UI.
- Native `core/lib/model.ts` binds lowering through `model-styles.ts` to the provider-free registry, with no default initialization. The existing public `@divlet/core/model` subpath uses `core/model.ts` for synchronous Node bundled-default composition; the standard browser export condition bypasses that entry and file mappings swap the lowering port for `browser-styles.ts`, an explicit `NO_STYLE_ENGINE` refusal. A physical parser-only Node copy runs the actual native binding without a test port substitution. Browser validation/native `style` maps do not imply utility compilation or declarative `styles` lowering; Node runtime/server/source dispatch likewise use the generic registries; the existing public runtime entry explicitly composes bundled defaults. Source-level provider-free writer isolation does not establish an installed public native-only host entry. No new public subpath or serialized capability field is introduced.
- CSS admission uses the same PostCSS grammar parser with source-map interpretation disabled. Browser bundling respects PostCSS's own optional-feature browser mappings; it adds no Node-global polyfill or alternate validator. `scripts/browser-model.mjs` owns source/installed model, codec and project verification bundle profiles plus a checkout-only private history-replay profile, all guarded against concrete engine/writer/Tailwind inputs and external imports. The kernel suite executes actual codec imports, annotation-looking inline/token round trips and computed CSS literals in Chromium, not a browser-only decoder. It returns bytes in memory, not a shipped standalone browser SDK artifact.
- `project.ts`, `codec.ts`, `diff.ts`, `ops.ts`, `prepare.ts`, `acceptance.ts` and `tools.ts` no longer reach Node built-ins. Concrete provider bootstrap remains Node-only, and canonical MIME parsing maps to an explicit `ASSETS_UNAVAILABLE` refusal in browser builds (no approximation of Node's WHATWG MIME canonicalization). Browser compatibility cannot be inferred from TypeScript compilation; `scripts/pages-build.mjs` refuses a host bundle that reaches Node/provider modules.
- `history-replay.ts` is the common item-to-candidate replay kernel for both writers, including guarded patch/lifecycle/order replay and endpoint version coalescing. Shared immutable-input/refusal vectors execute in Node and actual Chromium imports. Whole-project preparation/persistence, accepted-state publication, queues, stack selection and point authority remain in each host; this does not add a browser frame-reorder route or complete writer extraction. The replay verification bundle is a private source-checkout profile, not an installed/public browser API.
- The current style/provider, component and format-transition gaps remain relevant. An offline fork must not silently establish different cascade, override, resource or renderer rules.

## Recommended boundary: portable semantics, explicit hosts

```text
board UI / agent operation contract
  +-- browser host
  |     +-- shared portable semantic kernel
  |     +-- browser storage / file permission / download / projection
  +-- Node host
        +-- same portable semantic kernel
        +-- filesystem / watcher / loopback API / host bridge
```

The kernel should own representable project data, validation, patches, component expansion, resource/reference semantics and candidate/history transformations that do not require I/O. The browser continues to own layout and painting; no alternate canvas renderer is implied. Host-independent logic should have one implementation and shared test vectors, not a browser reimplementation that merely resembles the Node validator.

Hosts own persistence, publication, subscriptions, permissions and transport. In the connected local mode, Node remains the single accepted-state writer and validates requests through the same kernel; a thin host does not trust arbitrary browser claims. In offline mode, a browser session may become its own writer only for its locally opened copy, with an explicit persistence boundary and multi-tab ownership policy. Connecting later must not silently merge that copy or reuse another owner's History IDs.

A Web Worker can isolate expensive pure work from UI rendering. A Service Worker serves a different role: offline loading, cache updates and local resource responses. Neither worker choice supplies filesystem authority. Do not make an immortal Service Worker the sole owner of accepted project state, or put a permanent fake HTTP server between the UI and an in-browser kernel merely to preserve every existing route string.

Do not select a new package name or folder hierarchy before the dependency boundary earns it. Preserve current public standalone-entry/provider behavior while extracting a browser-safe entry; WEB-2 already records why root-only provider registration would break that behavior. Avoid blanket Node polyfills as a substitute for separating filesystem/compiler composition from semantic code.

## Read-session boundary

`web/lib/board-session.ts`, public as `@divlet/web/session`, owns the transport-free read port: `readState`, `readFrame` and `subscribe`, whose returned function ends that subscription. Events distinguish state/change payloads, host connection status and malformed state transport data. Payloads are `unknown`, not automatically accepted models; consumers retain their admission/cache/state guards. This is separate from the agent-host `Session` in `contract.ts` and grants no write, raw-route, upload or persistence authority.

`createSnapshotReadSession` clones host-provided state/frame data and every read/event result, freezes the capability object and prevents queued state delivery after immediate or reentrant unsubscribe. Constructing a snapshot does not validate a project or make private metadata publishable: the composition/publisher must curate and admit the input first. The same snapshot properties run in Node and actual browser ESM without HTTP.

The native client composes its JSON transport and HTTP/SSE reader in `web/lib/host.js`. The store keeps version/render-aware cache admission and the board keeps plugin-bootstrap ordering, reconnect feedback and change handling. JSON error projection and dynamic global-fetch instrumentation remain intact; native `EventSource` owns reconnects. `tsconfig.web.json` checks the four transport/service/composition modules against DOM libraries without Node ambient types, not the whole frontend.

Ephemeral shared selection is a separate optional `BoardSelectionPublisher`, not a writer added to `BoardReadSession`. The native host publishes through its existing selection POST. A fixed composition without that capability keeps selection browser-local, never starts a pending publication or falls back to HTTP, and uses host selection only as the initial seed. Later host reads cannot resurrect a cleared local selection or overwrite local frame/node choices; model/frame removal still prunes them. Native sequence, pending-response and failure-feedback semantics remain unchanged.

Preview measurements first update the client's observation cache and local events through the existing authenticated document channel. A separate optional `BoardObservationPublisher` controls sharing them with the native host. Without it the receiver still accepts current geometry, but starts no report timer or queued-publication bookkeeping and never falls back to an observations POST. Native publication retains its 180 ms coalescing, shown-render cursor, lifecycle cancellation and ignored transient refusals; the backend still validates render identity and geometry independently.

`web/lib/board-host.ts`, public as `@divlet/web/host`, separately types optional History and source-update services. They can carry native authority (`navigate`, reimport/open) and are never added to the read session. History reads are omitted when its service is absent; restore controls additionally require both the host's restore method and the state's navigation advertisement. A reader-only service may supply audit data without restore controls. Source-change scanning and its entire notification action workflow require the source-update service, so absence produces neither a scan nor an unsupported import prompt. Native adapters keep the same routes, captured History targets, generation guards, scan-failure policy and deduplicated notifications.

These gates are proven with actual activity/project/store modules under fixed test compositions. The complete board also runs on the static browser composition (`core/lib/browser-board.ts`), proven in Chromium against the built Pages set under a repository prefix (`web/tests/pages.mjs`). That is a host-replaceable board, not an offline one: there is no Service Worker, so a first visit and every reload need the static files.

## Public prepared-page inspection data

The build-side `core/lib/public-snapshot.ts` projector accepts an intentionally public prepared HTML page, a deliberate public label/viewport and a sibling HTML browsing filename. It uses the existing strict HTML codec, refuses script elements including editor metadata scripts, clears frame/node metadata and builds allowlisted state/descriptors. It never accepts `runtime.info()` as a state template: native paths/URLs, source/output/sidecar names, agent/history/client state and application metadata are not copied. Edit capabilities are explicitly false; the data itself is not whole-board read-only enforcement.

This is a flattened **inspection projection**, with presentation ID `index` and initial version 1, not the authored source project. Public `renderFile` pages have element anchors/styles but no `encodeHtml` metadata manifest; original text/component identities, source revisions and board geometry cannot be recovered from them. The viewport is supplied explicitly. Keep the prepared page and its styles unchanged as rendering authority; re-rendering the inspection model can change CSS layering and identities.

`scripts/landing-demo.mjs` reads the exact public bytes through `landingEntries` in `scripts/landing-hash.mjs`, the existing public-set/fingerprint/copy owner. It creates inspection data only: no alternate renderer, authored landing, source/cache write or publication. Ownership/hash verification is not source/cache freshness; the existing freshness check remains a publication gate. The content-derived snapshot ID is a view identity, not an attestation.

Public-content curation, HTML/model validity, publication provenance, reference closure and UI capabilities are different checks. This projector is not a secret scanner of visible authored text, attributes or CSS, nor a resource/link-graph validator. It does not make arbitrary input publishable. The first profile deliberately permits only a sibling `.html` browsing filename without paths, queries or fragments; broader routing needs an explicit contract rather than implicit URL guesses.

## Useful modes

- **Static publication:** ordinary rendered HTML/CSS/resources. This already exists and needs no editor runtime or service worker.
- **Static-hosted read-only demo:** load a deliberately public example project and its prepared frames into the real board UI. Clearly identify the demo/offline limitations. No fake agent connection, Stop control, filesystem save or unsupported edit operation. This can precede a complete offline editor if the read-only host contract genuinely reuses the same UI and projections.
- **Offline editor:** enable only operations the browser kernel and installed providers support. File System Access APIs require user permission and browser support; download/upload remains a fallback. IndexedDB/OPFS stores browser-local data, not an automatic save to the original repository file, and storage eviction/quota must not masquerade as durable filesystem persistence.
- **Connected host:** the existing local Node/CLI/MCP/Pi path, reached only through an explicitly chosen, authenticated connection. Capabilities come from the actual host; unsupported functions are absent, not guessed or cosmetically enabled.

Repository path prefixes are not origin isolation. Project sites under the same Pages hostname share an origin, and browser storage/file permissions are not private merely because application paths differ. A public demo should not persist private user projects by default; private editing needs an explicit storage policy and an appropriate origin/deployment boundary.

A first static visit may need the network. Reliable offline reopening additionally needs an explicit versioned cache/update strategy; it is not a consequence of being static HTML. Service Worker updates must not mix incompatible kernel, model and projection generations or cache authenticated API traffic indiscriminately.

## The landing as a real demonstration

The useful nesting is a static application shell opening an ordinary curated landing `.divlet` project. The iframe contains that project's content, not another recursively embedded copy of the editor. Keep an immediately readable explanation and installation command before or alongside an opt-in demo; forcing every visitor through the full editor would increase startup weight and obscure onboarding.

Copy-command buttons belong to trusted application-shell behavior, not arbitrary scripts hidden in inert project metadata. Clipboard writes require the relevant browser support/user action. Static hosts may not provide the Node server's configurable response headers. In particular, CSP `sandbox` cannot be supplied through a meta tag; prove iframe sandbox/referrer/channel behavior under the actual static host rather than assuming current server headers survive the move. Browser-only tool `path` arguments also cannot grant access to arbitrary OS files or bypass file-picker/handle permission.

A public demo project must be intentionally publishable: do not expose real project metadata, absolute resource paths, local credentials or unpublished work merely because the runtime needs model data. Opening a user's private project in the static editor must not upload it, auto-fetch its remote dependencies or pair with a local agent.

The core must not import a marketing project. A demo is composition-owned and opens an independently owned example. Existing `examples/landing/landing.divlet` and the single prepared public-set/fingerprint owner remain authoritative until an explicit, verified replacement; do not create a second manually maintained landing or relax private-output exclusions for a demo.

## Service Worker is not a public MCP endpoint

Implemented route (see [browser-hosted MCP](browser-mcp.md)): the agent side supplies the browser. `divlet-mcp --connect <url>` or `@divlet/core/browser-mcp` opens the static site in a managed Chromium and exchanges MCP 2026-07-28 messages with the page's provider by direct evaluation; nothing listens, relays or is deployed. That is an integrated agent-side adapter, not a generally reachable MCP server, and it does not change the points below.

A Service Worker intercepts requests for its controlled browser clients within its origin/scope. It does not accept arbitrary inbound TCP connections or cause a remote MCP client's requests to GitHub Pages to execute in the visitor's browser. It can emulate a local route for a controlled page; that is not a generally reachable MCP HTTP server. Background lifetime also cannot be assumed.

There are two useful, distinct agent routes:

- **Browser-mediated tools, including WebMCP:** the WebMCP draft exposes JavaScript functions with tool descriptions and input schemas to participating browser agents. This closely matches the proposed inversion: application logic stays client-side and the agent invokes it there. Share divlet's operation vocabulary, schema and validation instead of inventing another command set. Feature presence, agent integration, cancellation, errors, user control and browser permissions need real proof. The inspected specification is a Community Group draft; it does not establish universal browser availability or interoperability with existing stdio/Streamable HTTP clients.
- **An external agent bridge:** a small extension/local host/explicit relay can connect the browser session to a normal MCP client. The browser may initiate an outbound connection instead of listening as a server, but a reachable bridge and a defined transport still exist. A private MessagePort/custom channel can be an implementation detail, not an advertised standard network MCP endpoint. Do not introduce a cloud relay, remote dependency or public listener by default. HTTPS/mixed-content rules, CSP and local-network permissions must be tested for the chosen browser/bridge path; an outbound connection is not guaranteed merely because a loopback endpoint exists.

A bridge must pair an exact origin, document, project and session through explicit user intent, preserve revision/single-writer checks and rotate capabilities after navigation/reconnect. No wildcard CORS, silent localhost probing, persisted session tokens in project content or automatic exposure of local files to a hosted page. Preserve the current authenticated document-bound preview channel and no-referrer boundaries.

## Evidence required before changing product claims

- Extend the proven standalone-frame browser closure as project/session operations are admitted; retain shared validation, candidate/refusal and size/Unicode vectors and no host/bootstrap leakage. Source-profile native-browser execution and installed-profile bundling/Node smoke are distinct checks, not proof of installed browser execution or universal browser compatibility.
- A real static-server test loads the chosen demo path with no `api/*` or SSE backend, missing-asset rescue or hidden Node process. Test repository prefixes, clean first load, subsequent offline reload, cache updates, accurate capabilities and bounded startup cost.
- Offline mutation proof covers candidate acceptance/refusal, undo/redo, local persistence failure, download/reopen and two-tab ownership. Missing renderer requirements must diagnose/read-only rather than silently return empty styling.
- A browser-agent experiment distinguishes WebMCP tool registration/execution from a conventional external MCP transport. An actual client must call a tool, receive a refusal and cancel work; feature detection alone is insufficient.
